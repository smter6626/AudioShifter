# AudioShifter macOS 复刻：静态合同

> 文档类型：`static.md`
>
> 作用：记录 macOS 复刻任务中长期稳定、原则上不随单次开发步骤变化的背景、目标、范围和设计约束。
>
> 本文档不记录当前执行步骤、临时命令、排错过程、完成记录或短期计划；这些内容应写入对应的 `runtime.md`。已确认行为的详细合同见 `macos/design/behavior_spec.md`，模块边界见 `macos/design/architecture_plan.md`，验证映射见 `macos/design/verification_matrix.md`。

## 1. 项目背景

AudioShifter 是一个面向非技术用户的本地音频变调与变速工具。原始可用版本运行于 Windows，使用 Python 和 Tkinter 提供图形界面，并通过 FFmpeg 与 Rubber Band 完成音频解码、变调、变速和重新编码。

原始 Windows 版本曾包含基于机器码、激活码和本地授权文件的使用限制。当前项目不再需要任何加密、机器绑定、注册码或激活流程，新版本应移除相关逻辑，不在其他平台重新实现。

macOS 版本的原始代码已经遗失，目前可用的参考材料是本地保存的 Windows 源代码、构建配置、依赖文件和成品。macOS 任务的性质是基于现有行为重新实现和整理，而不是恢复已经遗失的旧代码。

Windows 历史实现只作为产品行为和音频处理方向的参考。其源码、文档和打包配置后续不修改、不清理、不重构；其中的激活机制、固定临时文件、静默覆盖和线程问题不得迁移到新平台。

## 3. macOS 复刻目标

macOS 任务的目标是交付一个可以由普通用户直接运行的图形化应用，使用户无需安装 Python、FFmpeg、Rubber Band、Homebrew 或其他开发环境，即可完成音频文件的变调和变速处理。

交付结果应至少满足以下条件：

1. 在 Apple Silicon Mac 上以标准应用形式启动。
2. 提供中文图形界面。
3. 允许用户选择受支持的本地音频文件。
4. 允许用户设置整数半音变调值。
5. 允许用户设置相对于原速度的变化百分比。
6. 在不修改源文件的前提下生成新的音频文件。
7. 默认把结果保存到当前用户的下载目录。
8. 向用户明确显示处理状态、成功结果和可理解的失败原因。
9. 应用自身携带运行所需的音频处理依赖，不要求用户手动放置命令行程序或动态库。
10. 不包含机器码、激活码、注册机、许可证文件校验或其他访问限制。

## 4. 核心功能合同

### 4.1 输入

第一阶段只承诺以下输入范围：

- MP3
- M4A
- WAV
- FLAC

扩展名匹配不区分大小写。程序不能只依赖扩展名判断媒体有效性；损坏文件、零字节文件、非音频内容或无法解码的文件必须明确失败。

如果底层工具可以读取更多格式，不应仅凭底层能力自动扩大产品承诺；新增格式必须经过明确测试后再加入界面和文档。

### 4.2 变调参数

变调参数使用半音（semitone）作为相对变化单位：

- `0` 表示保持原调。
- 正整数表示升调。
- 负整数表示降调。
- 不允许小数半音。
- 允许范围固定为 `-24` 至 `+24`，上下界均可取。

超出范围、非整数、非有限数值或包含无效单位字符的输入必须在启动外部处理前拒绝。

### 4.3 变速参数

变速参数使用**相对于原速度的变化百分比**，不是最终播放速度百分比：

- `0` 表示原速。
- `+20` 表示加速 20%，最终速度为原速度的 120%。
- `-20` 表示减速 20%，最终速度为原速度的 80%。
- 用户不输入 `%`，百分号由界面说明和输出文件名添加。
- 数值允许有限小数。
- 允许范围固定为 `-95` 至 `+400`，上下界均可取。

传给 Rubber Band 的 tempo multiplier 为：

```text
tempo_ratio = 1 + speed_change / 100
```

因此首阶段实际速度范围为原速度的 5% 至 500%。超出范围或无效输入必须在启动外部处理前拒绝。

### 4.4 音频处理语义

音频处理的稳定语义为：

1. 使用 FFmpeg 解码并标准化输入音频。
2. 中间工作音频为 44.1 kHz、双声道、PCM signed 16-bit WAV。
3. 使用 Rubber Band 同时执行整数半音变调与时间伸缩。
4. 使用 R3/finer 精细处理方向。
5. 启用 formant preservation 共振峰保持方向。
6. 使用 FFmpeg 和 `libmp3lame` 编码结果。
7. 保留原始输入文件。

最终输出固定为：

- MP3
- 320 kbps
- 44.1 kHz
- 双声道

第一阶段不复制、不承诺保留源文件的标题、艺术家、专辑、封面、歌词、章节或其他元数据；只保证音频内容可以正常处理并生成可播放结果。

### 4.5 输出位置

成功结果固定保存到当前用户的下载目录：

```text
~/Downloads/
```

程序不默认保存到输入文件目录，也不在每次处理时要求用户选择保存位置。

处理开始前必须检查下载目录存在、确实是目录且可写。路径不存在、路径不是目录、没有写入权限或磁盘空间不足时，应弹窗说明具体原因并终止任务，不自动切换到其他目录。

### 4.6 输出命名

输入文件为 `name.ext`，变调参数为 `x`，速度变化参数为 `y` 时，基础输出文件名固定为：

```text
name<x><y>%.mp3
```

规则：

- `name` 为去除最后一个扩展名后的原文件名。
- `x` 始终显式带符号，零写作 `+0`。
- `y` 始终显式带符号，零写作 `+0%`。
- 速度小数使用 `.`，去除无意义尾随零。
- 两个参数都必须保留，不因零值省略。

示例：

```text
name+3+20%.mp3
name-3-20%.mp3
name+3-12.5%.mp3
name+0+0%.mp3
```

### 4.7 同名输出

程序永远不得覆盖或删除下载目录中的已有文件。

若基础名称已经存在，应选择第一个可用的自动递增名称：

```text
name+3+20%.mp3
name+3+20%_2.mp3
name+3+20%_3.mp3
```

发生冲突时必须弹窗提示：原目标已存在、不会覆盖，以及本次实际采用的新文件名或完整路径。用户确认后继续处理，无需手工修改名称。

编码前必须再次检查路径安全，防止外部程序在处理期间创建同名文件。

## 5. 技术方向

macOS 第一阶段沿用 Python 技术栈，以降低复刻成本并最大限度复用已验证的处理方向：

- Python：应用逻辑
- Tkinter：桌面图形界面
- FFmpeg：音频解码、标准化、MP3 编码与媒体探测
- Rubber Band：变调与变速
- PyInstaller：生成 macOS 应用包

当前已验证的开发环境基线为 Python 3.11、Tkinter/Tcl/Tk 8.6、FFmpeg 8.1、Rubber Band 4.0 和 PyInstaller 6.21。具体修订版本和安装证据记录在 `macos/environment_report.md`；长期合同不保证 Homebrew 修订号永远不变。

应用代码应将用户界面、控制层、音频管线、外部程序适配、路径与依赖解析、参数校验、输出命名、临时资源和错误表示分离，避免继续维持所有逻辑集中于单个 GUI 文件的结构。

## 6. 平台与分发边界

第一阶段只支持 Apple Silicon `arm64`：

- 不支持 Intel Mac。
- 不制作通用二进制。
- 不把 Rosetta 运行作为合格环境。
- 不考虑 Developer ID 签名。
- 不考虑 Apple 公证。
- 不以 Mac App Store 上架为目标。

产品功能本身不依赖特定 macOS 版本，但实际最低兼容版本由最终 Python、Tcl/Tk、第三方依赖、PyInstaller 产物和实机验证共同决定。在完成对应测试前，不提前承诺最低 macOS 版本。

无论采用何种打包方式，最终交付物不应要求普通用户执行终端命令、安装 Homebrew、配置 PATH 或手动下载依赖。

## 7. 任务与交互边界

### 7.1 单任务

同一应用实例同一时间只允许一个处理任务。处理期间禁用重复启动，控制层也必须拒绝第二个任务，不能只依赖按钮状态。

### 7.2 后台处理

音频处理必须在后台执行，不得阻塞 Tkinter 主线程。后台线程不得直接更新 Tkinter 控件，所有 UI 更新必须调度回主线程。

### 7.3 取消

处理期间提供取消功能。取消应终止当前 FFmpeg 或 Rubber Band 子进程、阻止后续阶段、删除残缺输出并清理临时工作区。取消属于正常终止状态，不应显示为普通失败。

### 7.4 关闭窗口

处理期间关闭窗口时，必须询问是否取消当前任务并退出：

- 用户选择继续处理：保持窗口和任务。
- 用户确认退出：执行取消流程，清理后退出。

不得直接遗留后台子进程。

## 8. 代码与仓库原则

### 8.1 应纳入版本控制

- 经过整理的应用源代码
- 构建配置
- 可重复执行的构建脚本
- 项目文档
- 测试代码与必要的小型测试资源
- 第三方依赖的许可证和来源说明

### 8.2 原则上不纳入版本控制

- 原始 Windows 构建目录
- `dist/`、`build/` 等可重新生成的构建产物
- Windows `.exe`、`.dll` 和本地授权文件
- 机器专属配置
- 虚拟环境
- 临时音频文件
- 用户输入与输出音频
- 打包后的 `.app`、`.dmg` 或安装包
- 签名私钥、证书私钥或其他秘密信息

第三方可执行文件或动态库是否提交到仓库，应根据可重复构建、文件体积、GitHub 限制和许可证要求单独判断，不应默认照搬原始目录。

## 9. 质量要求

### 9.1 稳定性

- 每次处理使用独立系统临时目录或唯一临时资源。
- 临时文件不得写入 Downloads、输入目录或仓库目录。
- 无论成功、失败还是用户取消，临时资源都应尽可能清理。
- 同名输出、Downloads 不可用、只读路径、空间不足和依赖故障必须得到显式处理。
- 只有通过最终媒体验证的文件才能作为成功结果保留。
- 失败和取消不得保留被误认为成功结果的残缺 MP3。

### 9.2 可诊断性

程序不能只显示“处理失败”或子进程退出码。内部应保留足以诊断问题的 FFmpeg、FFprobe、Rubber Band 和应用错误信息；面向普通用户的提示应说明错误类别和可采取的动作。

错误模型至少覆盖：

- 输入不存在、不可读、不支持或媒体损坏
- 变调、变速参数无效
- Downloads 不存在、不是目录或不可写
- 磁盘空间不足
- 依赖缺失或不可执行
- 解码、处理、编码失败
- 输出名称冲突
- 用户取消
- 临时资源清理警告

日志不得包含用户音频内容或不必要的隐私信息。若记录文件路径，应明确其仅保存在本地。

### 9.3 易用性

主要使用者是非技术用户，因此界面设计优先级为：

1. 操作路径明确。
2. 参数单位和正负方向明确。
3. 默认值安全且符合常见用途。
4. 状态、冲突提示和结果路径可理解。
5. 减少文件系统知识要求。
6. 高级能力不得妨碍基础使用。

第一阶段不要求虚构的精确进度百分比；明确的阶段状态优先于不准确的进度数字。

## 10. 安全与隐私

- 所有音频处理默认在本地完成。
- 不上传用户音频。
- 不要求账户、网络连接或远程授权。
- 不采集遥测数据，除非未来经过明确设计和用户同意。
- 不执行来自用户输入的任意 Shell 字符串。
- 外部程序调用必须使用参数数组并禁用 Shell 解释。
- 应验证和规范化输入参数，避免命令注入和非预期路径操作。
- 清理逻辑只能删除当前任务创建且已验证位于系统临时目录中的资源。

## 11. 第三方许可证

FFmpeg、Rubber Band 及其构建中启用的其他组件具有各自许可证要求。项目必须记录实际使用的版本、构建方式、来源和许可证文本。

当前已验证的 Homebrew FFmpeg 构建启用了 GPL/version 3 组件；Rubber Band 使用 GPL-2.0-or-later 或商业许可双重授权。项目在分发二进制前必须确定 GPL 兼容路线或商业许可路线，并确定 notices、许可证文本和对应源码的提供方式。

是否允许闭源分发、是否需要提供对应源代码，以及最终应用受何种许可证约束，取决于实际构建和分发方式，不能仅凭“免费使用”或“非商业用途”作出判断。

许可证方案未完成不会阻塞本地行为规格、测试和实现，但会阻塞正式二进制分发。

## 12. 与 Android 阶段的关系

Android 移植是 macOS 复刻之后的独立阶段。macOS 阶段应形成清晰、可测试的产品行为合同和音频处理语义，为 Android 提供参考，但不要求 Tkinter、PyInstaller、桌面文件路径或子进程实现能够直接复用到 Android。

应优先共享以下内容：

- 参数定义与范围
- 相对速度变化语义
- 输出音频语义
- 文件命名规则
- 同名输出规则
- 错误类别
- 测试音频与预期结果
- 用户体验原则

Android 平台的界面、文件访问、原生库接入、APK 签名和分发机制将在后续任务中单独设计。
