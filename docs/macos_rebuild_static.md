# AudioShifter macOS 复刻：静态合同

> 作用：记录 macOS 复刻任务中长期稳定、原则上不随单次开发步骤变化的背景、目标、范围和设计约束。

> 本文档不记录当前执行步骤、临时命令、排错过程、完成记录或短期计划；这些内容应写入对应的 `runtime.md`。

## 1. 项目背景

AudioShifter 是一个面向非技术用户的本地音频变调与变速工具。原始可用版本运行于 Windows，使用 Python 和 Tkinter 提供图形界面，并通过 FFmpeg 与 Rubber Band 完成音频解码、变调、变速和重新编码。

原始 Windows 版本曾包含基于机器码、激活码和本地授权文件的使用限制。当前项目不再需要任何加密、机器绑定、注册码或激活流程，新版本应移除相关逻辑，不在其他平台重新实现。

macOS 版本的原始代码已经遗失，目前可用的参考材料是本地保存的 Windows 源代码、构建配置、依赖文件和成品。macOS 任务的性质是基于现有行为重新实现和整理，而不是恢复已经遗失的旧代码。

## 3. macOS 复刻目标

macOS 任务的目标是交付一个可以由普通用户直接运行的图形化应用，使用户无需安装 Python、FFmpeg、Rubber Band 或其他开发环境，即可完成音频文件的变调和变速处理。

交付结果应至少满足以下条件：

1. 在目标 macOS 设备上以标准应用形式启动。
2. 提供中文图形界面。
3. 允许用户选择受支持的本地音频文件。
4. 允许用户设置变调半音数。
5. 允许用户设置相对于原音频的速度百分比。
6. 在不修改源文件的前提下生成新的音频文件。
7. 向用户明确显示处理状态、成功结果和可理解的失败原因。
8. 应用自身携带运行所需的音频处理依赖，不要求用户手动放置命令行程序或动态库。
9. 不包含机器码、激活码、注册机、许可证文件校验或其他访问限制。

## 4. 核心功能合同

### 4.1 输入

第一阶段应保持与现有 Windows 程序实际界面一致的输入范围：

- MP3
- M4A
- WAV
- FLAC

如果底层工具可以读取更多格式，不应仅凭底层能力自动扩大产品承诺；新增格式必须经过明确测试后再加入界面和文档。

### 4.2 参数

变调参数使用半音（semitone）作为单位：

- `0` 表示保持原调。
- 正数表示升调。
- 负数表示降调。
- 底层处理应允许小数值，但界面是否向普通用户突出小数输入可在实现阶段决定。

变速参数使用源音频速度的百分比表示：

- `100` 表示原速。
- 小于 `100` 表示减速。
- 大于 `100` 表示加速。
- 参数必须大于 `0`。

普通界面应优先防止明显无意义或可能造成异常资源消耗的极端参数。具体限制属于实现和测试决策，不在静态合同中固定为未经验证的数值。

### 4.3 音频处理语义

音频处理的稳定语义为：

1. 解码输入音频。
2. 使用 Rubber Band 执行变调与时间伸缩。
3. 在变调过程中尽可能保持共振峰特征，延续原程序使用 `formant` 相关处理的方向。
4. 将结果编码为 MP3。
5. 保留原始输入文件。

应优先保证变调和变速可以同时生效，且二者的含义与原 Windows 版本一致。

### 4.4 输出

- 默认输出格式为 MP3。
- 输出文件应与输入文件具有可辨识的名称关系。
- 文件名应包含足以识别变调和速度参数的信息。
- 不得在用户无感知的情况下覆盖已有文件。
- 输出位置必须对用户可理解、可访问。
- 临时文件不得长期暴露在用户的下载目录或源文件目录中。

具体命名格式、覆盖处理方式和保存交互可以在实现阶段确定，但一旦形成用户可见合同，应通过测试和文档保持一致。

## 5. 技术方向

macOS 第一阶段沿用 Python 技术栈，以降低复刻成本并最大限度复用现有处理逻辑：

- Python：应用逻辑
- Tkinter：桌面图形界面
- FFmpeg：音频解码与 MP3 编码
- Rubber Band：变调与变速
- PyInstaller：生成 macOS 应用包

该技术选择是 macOS 复刻阶段的默认方向。除非在实现中出现无法合理解决的平台兼容性、分发或维护问题，否则不应仅为技术重写而改用全新的桌面框架。

应用代码应将用户界面、音频处理、路径与依赖解析、参数校验和错误表示分离，避免继续维持所有逻辑集中于单个 GUI 文件的结构。

## 6. 平台与分发边界

第一阶段优先保证当前开发设备和实际使用设备上的可运行性。是否同时支持 Intel Mac、是否制作通用二进制（universal binary）、是否进行 Developer ID 签名和 Apple 公证，应基于实际分发对象与测试结果决定，不在缺少需求时提前承诺。

无论采用何种打包方式，最终交付物不应要求普通用户执行终端命令、安装 Homebrew、配置 PATH 或手动下载依赖。

本任务不以 Mac App Store 上架为目标。若未来改变分发方式，应重新审查签名、公证、沙盒和第三方许可证约束。

## 7. 代码与仓库原则

### 7.1 应纳入版本控制

- 经过整理的应用源代码
- 构建配置
- 可重复执行的构建脚本
- 项目文档
- 测试代码与必要的小型测试资源
- 第三方依赖的许可证和来源说明

### 7.2 原则上不纳入版本控制

- 原始 Windows 构建目录
- `dist/`、`build/` 等可重新生成的构建产物
- Windows `.exe`、`.dll` 和本地授权文件
- 机器专属配置
- 临时音频文件
- 用户输入与输出音频
- 签名私钥、证书私钥或其他秘密信息

第三方可执行文件或动态库是否提交到仓库，应根据可重复构建、文件体积、GitHub 限制和许可证要求单独判断，不应默认照搬原始目录。

## 8. 质量要求

### 8.1 稳定性

- 后台音频处理不得使界面失去响应。
- 图形界面更新必须遵循 Tkinter 的线程安全边界。
- 每次处理应使用独立的临时目录或唯一临时文件。
- 无论成功、失败还是用户取消，临时资源都应尽可能清理。
- 同名输出、只读目录、空间不足和依赖故障必须得到显式处理。

### 8.2 可诊断性

程序不能只显示“处理失败”或子进程退出码。内部应保留足以诊断问题的 FFmpeg、Rubber Band 和应用错误信息；面向普通用户的提示应说明错误类别和可采取的动作。

日志不得包含不必要的用户隐私信息。若记录文件路径，应明确其仅保存在本地。

### 8.3 易用性

主要使用者是非技术用户，因此界面设计优先级为：

1. 操作路径明确。
2. 默认值安全且符合常见用途。
3. 状态和结果可理解。
4. 减少手动输入和文件系统知识要求。
5. 高级能力不得妨碍基础使用。

## 9. 安全与隐私

- 所有音频处理默认在本地完成。
- 不上传用户音频。
- 不要求账户、网络连接或远程授权。
- 不采集遥测数据，除非未来经过明确设计和用户同意。
- 不执行来自用户输入的任意 Shell 字符串；外部程序调用应使用参数数组。
- 应验证和规范化输入参数，避免命令注入和非预期路径操作。

## 10. 第三方许可证

FFmpeg、Rubber Band 及其构建中启用的其他组件具有各自许可证要求。项目必须记录实际使用的版本、构建方式、来源和许可证文本。

是否允许闭源分发、是否需要提供对应源代码，以及最终应用受 LGPL、GPL 或商业许可中的哪一种约束，取决于实际构建和链接方式，不能仅凭“免费使用”或“非商业用途”作出判断。

在许可证路径尚未确认前，不应在公开发布说明中作出与实际许可证不一致的授权承诺，也不应继续沿用原指南中仅以“禁止商业用途”概括第三方组件授权的做法。

## 11. 与 Android 阶段的关系

Android 移植是 macOS 复刻之后的独立阶段。macOS 阶段应形成清晰、可测试的产品行为合同和音频处理语义，为 Android 提供参考，但不要求 Tkinter、PyInstaller、桌面文件路径或子进程实现能够直接复用到 Android。

应优先共享以下内容：

- 参数定义
- 输出语义
- 文件命名规则
- 错误类别
- 测试音频与预期结果
- 用户体验原则

Android 平台的界面、文件访问、原生库接入、APK 签名和分发机制将在后续任务中单独设计。
