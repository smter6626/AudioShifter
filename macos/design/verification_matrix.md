# AudioShifter macOS 验证矩阵

> 文档定位：本文件是 macOS 第一阶段的**合同验证清单**，把 `behavior_spec.md` 中的每条用户可见规则映射为可执行测试或审查项。
>
> 本文件不是测试结果报告。初始状态统一为“待实现”或“待执行”；只有实际测试代码、命令输出或人工界面验证完成后才能改为通过。
>
> 模块边界和测试分层见 `architecture_plan.md`；长期原则见 `docs/macos_rebuild_static.md`；执行进度应写入 `docs/macos_rebuild_runtime.md`。

## 1. 验证原则

1. 先验证纯函数和文件系统行为，再验证真实 FFmpeg/Rubber Band 管线，最后验证 GUI。
2. 正常路径、边界值、失败路径和取消路径必须同时覆盖。
3. Windows 历史程序的实际输出只能作为参考证据，不能替代新合同测试。
4. FFmpeg 能读取更多格式不等于产品支持更多格式。
5. 环境冒烟测试通过不等于正式实现通过。
6. 所有真实音频测试使用合成或明确允许提交的小型测试素材，不使用用户私人音频。
7. 测试产生的音频默认位于系统临时目录，不提交仓库；正式测试夹具另行审查。
8. 每次测试记录实际依赖版本、命令、退出码和关键媒体信息。

## 2. 状态与优先级

### 状态

- `待实现`：对应模块或测试尚未创建
- `待执行`：测试已存在但尚未运行
- `通过`：实际结果符合预期
- `失败`：实际结果不符合预期
- `阻塞`：外部条件导致无法验证
- `不适用`：经合同变更确认后不再适用

### 优先级

- `P0`：进入 GUI 开发前必须通过
- `P1`：首个可用 GUI 版本前必须通过
- `P2`：打包或发布前验证

## 3. 证据类型

| 证据类型 | 说明 |
|---|---|
| 单元测试 | 不启动外部二进制的自动化测试 |
| 集成测试 | 启动 FFmpeg、FFprobe 或 Rubber Band 的自动化测试 |
| 文件系统测试 | 使用临时目录和权限模拟验证路径行为 |
| GUI 人工测试 | 实际操作 Tkinter 界面并记录结果 |
| 代码审查 | 检查依赖方向、安全调用、无禁用逻辑 |
| 媒体探测 | 使用 FFprobe 检查编码、采样率、声道和时长 |
| 进程检查 | 验证取消后无遗留子进程 |
| 仓库检查 | 验证未提交临时音频、环境和二进制 |

## 4. 测试数据约定

建议后续生成以下小型合成素材：

| Fixture ID | 内容 | 用途 |
|---|---|---|
| `AUDIO-WAV-001` | 4 秒、44.1 kHz、双声道正弦 WAV | 标准管线 |
| `AUDIO-MP3-001` | 由标准 WAV 转换的 MP3 | MP3 输入 |
| `AUDIO-M4A-001` | 由标准 WAV 转换的 AAC/M4A | M4A 输入 |
| `AUDIO-FLAC-001` | 由标准 WAV 转换的 FLAC | FLAC 输入 |
| `AUDIO-MONO-001` | 单声道输入 | 标准化为双声道 |
| `AUDIO-48K-001` | 48 kHz 输入 | 标准化为 44.1 kHz |
| `AUDIO-CORRUPT-001` | 截断或损坏的音频 | 解码失败 |
| `AUDIO-FAKE-001` | 非音频文本改名为 `.mp3` | 内容伪装 |
| `AUDIO-ZERO-001` | 零字节文件 | 输入预检 |

素材文件名还应生成特殊路径变体：

```text
中文 音频 (test) & sample.mp3
song.final.v2.MP3
quote'file.wav
```

## 19. 阶段退出标准

行为合同验证阶段只有在以下条件满足后才能关闭：

1. 三份设计文档相互引用且无冲突。
2. static 中的长期参数语义与本规格一致。
3. 速度语义统一为相对变化百分比，`0` 为原速。
4. 变调范围和速度范围已固定。
5. Downloads 输出、命名、零值、递增冲突规则已固定。
6. 44.1 kHz、双声道、320 kbps MP3 已固定。
7. 单任务、取消和关闭流程已固定。
8. 元数据不保留已明确。
9. 每个稳定合同至少存在一个验证项。
10. 下一 active step 可以直接依照本矩阵创建测试，不需要重新猜测产品行为。
